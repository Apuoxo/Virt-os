# Аудит исходной базы: ReactOS

Дата аудита: 2026-10-15

## 1. Решение по архитектуре

Для цели Windows NT-совместимости разумнее начать с существующей реализации Windows-подобных системных интерфейсов, чем пытаться добавить выполнение произвольных драйверов Windows в Linux. ReactOS выбран как исследуемая база, но это не обещание совместимости со всеми драйверами Windows 10/11 или современными играми.

Upstream: https://github.com/reactos/reactos  
Основная ветка upstream: `master`  
Лицензия репозитория upstream: GPL-2.0 (перед копированием/изменением исходников соблюдать лицензию и уведомления).

## 2. Что подтверждено проверкой

- Репозиторий upstream доступен публично; основная ветка называется `master`.
- В upstream есть сборочный workflow `.github/workflows/build.yml`.
- Официальная инструкция `INSTALL` описывает сборку через ReactOS Build Environment (RosBE), CMake и Ninja.
- Для загрузочного CD ISO upstream использует цель `bootcd`; в инструкции текущий артефакт называется `ReactOS.iso`, а в CI workflow используется путь `build/bootcd.iso`.
- Upstream CI собирает несколько сочетаний архитектур/компиляторов/конфигураций; это полезный ориентир, но копировать весь matrix в первый проектный workflow не нужно.
- Репозиторий `Apuoxo/Virt-os` имеет отдельный чистый `main` с коротким README. Старые ветки содержат другой bare-metal эксперимент и не подходят как ядро NT-совместимой системы.

## 3. Ограничения и риски

- Нельзя считать загрузку драйвера равной его работоспособности: нужны проверки PnP, IRP, прерываний, DMA, питания, отмены запросов и отказоустойчивости.
- Совместимость зависит от версии Windows NT, целевой архитектуры (x86/x64), WDM/KMDF/UMDF, используемых undocumented-интерфейсов, подписи и требований к безопасности.
- Современные античиты, графические драйверы и драйверы, ожидающие более новые версии Windows, относятся к отдельным высокорисковым направлениям.
- QEMU проверяет базовую загрузку и виртуальные устройства, но не доказывает поддержку физического ноутбука или его драйверов.
- Внешние build-скрипты не должны запускаться без проверки происхождения и фиксации версии.

## 4. Этапы

### Этап A — baseline и воспроизводимая сборка
1. Зафиксировать версию upstream ReactOS (конкретный commit SHA).
2. Выбрать проверяемый toolchain и задокументировать все версии.
3. Добавить узкий workflow для сборки x86 ISO; не запускать полный matrix на первом шаге.
4. Проверить наличие ISO, размер, контрольную сумму и метаданные.
5. Сохранить логи и ISO как GitHub Actions artifacts.

### Этап B — виртуальная загрузка
1. Запустить именно собранный ISO в QEMU.
2. Проверить, что прошивка видит ISO и запускается загрузчик.
3. Сохранить QEMU log и код завершения.
4. Отдельно описать, что автоматический smoke-test проверил, а что требует визуального или ручного теста.

### Этап C — аппаратная матрица
Для каждого драйвера фиксировать: файл и версия драйвера, целевая версия Windows, PCI ID/USB ID, архитектура, этап загрузки, обнаружение устройства, успешная инициализация, фактический функциональный тест, журнал ошибок.

### Этап D — собственные изменения
Только после успешного baseline: небольшие изолированные патчи, по одному логическому изменению, с повторением сборки и QEMU-теста.

## 5. Критерии первого успеха

Первый этап не считается завершённым, пока не есть:
- успешный CI build из зафиксированного исходного commit;
- проверенный bootable ISO как artifact;
- QEMU smoke-test с логом;
- commit SHA и ссылки на CI/artifacts;
- честный список оставшихся непроверенных функций.
